# EPUB → Kindle Conversion Audit

> Requirement identities, fixed inputs and assertions are derived from external standards/official Kindle guidance, independent format references, and the user-approved product contract. Production source is the system under test, not a requirement authority.

## 1. Audit independence rule

Canonical direction:

```text
External authority / product contract
        ↓
Requirement
        ↓
Audit Group + Fixed Inputs
        ↓
Assertions (frozen before implementation inspection)
        ↓
Independent E2E / reference / device evidence
        ↓
PASS / FAIL / PENDING / GAP / N/A
```

Production code is the system under test. It is never the expected-value authority. `tests/audit_support/palm.rs` parses generated bytes independently and does not import production parser/serializer modules or constants.

### Unsupported Feature Handling Principle

This audit adopts the following product-level conversion principle for valid EPUB input:

> If an EPUB contains a Kindle-unsupported or partially supported feature, the converter MUST preserve a usable reading result whenever readable body content, fallback content, or ordinary resources can be retained safely. Whole-publication rejection is a last resort, not the default unsupported-feature behavior.

Handling preference is evaluated in this order:

```text
PRESERVE
    ↓
TRANSPORT
    ↓
FALLBACK
    ↓
DROP-FEATURE
    ↓
DEGRADE
    ↓
REJECT
```

The categories mean:

- `PRESERVE`: preserve supported semantics normally.
- `TRANSPORT`: carry source semantics through without claiming converter-side interpretation when the Kindle target can safely receive them.
- `FALLBACK`: retain a defined or usable fallback representation when the primary feature is unsupported.
- `DROP-FEATURE`: remove only the unsupported behavior while retaining readable static content.
- `DEGRADE`: intentionally reduce unsupported structure to a meaningful readable representation.
- `REJECT`: reject the publication only when the preceding strategies cannot produce a safe, meaningful reading result, or when the input itself is invalid/unsafe.

KindleGen same-input final output is strong writer-behavior evidence for choosing among these handling classes, but it is not a byte-for-byte normative authority. EPUB specifications, official Amazon guidance, independent output inspection, and physical Kindle behavior remain part of the authority/evidence chain.

Security requirements such as “scripts are never executed” remain in force. This principle changes the required conversion response from “unsupported implies rejection” to “unsupported behavior must be made safe while preserving readable content where possible.”

### Unsupported Feature Policy Map

The following map is the canonical decision policy for valid EPUB input containing Kindle-unsupported, partially supported, or publishing-guideline-sensitive features. Fine-grained HTML tags, CSS constructs, and numeric boundaries are test vectors under these category-level policies rather than independent top-level Requirements.

#### Exit status contract

```text
0 = success
1 = success with warnings
2 = failure
```

A warning means conversion completed, but the converter intentionally dropped, substituted, degraded, or accepted a feature/condition whose original semantics cannot be guaranteed completely. Epub3-Kindle does not attempt byte-for-byte or warning-for-warning KindleGen parity; the exit status preserves only the high-level distinction between clean success, warning-success, and failure.

#### Warning categories

| Code | Category | Meaning |
|---|---|---|
| `W001` | Interactive / executable | Executable or interactive semantics were neutralized or degraded while readable static content was preserved. |
| `W002` | Rich / alternate content | A fallback or alternate representation was selected because the primary mechanism is not fully supported. |
| `W003` | Timed / media | Playback, synchronization, or timed-media semantics were dropped or degraded while readable content was preserved. |
| `W004` | Presentation | Unsupported presentation semantics were transported, ignored, or degraded and visible presentation may differ. |
| `W005` | Structured semantics | Unsupported structured semantics were reduced to a meaningful readable representation. |
| `W006` | Publishing guidance | An Amazon/Kindle publishing guideline boundary was exceeded, but conversion remained safe and feasible. |

#### KindleGen characterization evidence

The Policy Map above is informed by same-input KindleGen characterization of valid or processable EPUB cases. This evidence is writer-behavior evidence, not byte-for-byte authority.

Observed warning-success (`exit 1` with output generated) includes:

- individual HTML/XHTML content at 29,999,999, 30,000,000, and 30,000,001 bytes;
- 299, 300, and 538 HTML/XHTML content documents;
- inline/external script, form controls, Media Overlay, audio/video, unsupported CSS selectors/generated content/counters, MathML, `srcset`, `picture/source`, and `object`;
- HTML cover page in spine, reflowable `position:absolute/fixed/sticky`, unsupported image plus fallback, remote CSS `@import`, and remote CSS `url()`;
- fixed-layout viewport variants including numeric baseline, `px` suffixes, whitespace variation, reversed order, extra directives, semicolon separators, device dimensions, missing height, and duplicate width.

For the viewport set, KindleGen generated output for all nine characterization inputs. Numeric `600x800` and reversed-order controls produced `original-resolution=600x800`; duplicate width resolved to `700x800`. Other non-canonical forms still produced output even where no `original-resolution` was observed. Therefore a recoverable or ignorable viewport form is not, by itself, a conversion-impossibility boundary.

`rendition:align-x-center` is distinct: valid spine-item usage is not a UFH reject case and Epub3-Kindle accepts it. Publication-level placement is outside that valid spine usage and remains subject to package-validity handling rather than graceful unsupported-feature degradation.

#### Hard-reject boundary

The policy map does **not** weaken structural validity or security requirements. Whole-publication `REJECT` / exit `2` remains appropriate when safe conversion cannot produce a valid usable artifact, including cases such as:

- malformed/unreadable ZIP or OCF container;
- path traversal or paths escaping the EPUB container;
- encrypted resources that cannot be read for conversion;
- compression methods the converter cannot safely decode;
- package/XML damage that prevents reliable package interpretation;
- missing essential reading-order resources where a valid reading order cannot be reconstructed;
- broken fallback cycles with no usable target;
- product resource-safety limits / decompression-bomb conditions;
- cases where producing output would require inventing essential reading content or would silently create material corruption with no safe fallback/degradation path.

Amazon publishing guidance (for example the 30 MB individual-content-document guidance or 300-content-document guidance) is **not** itself a hard-reject boundary. Same-input KindleGen characterization demonstrated successful output beyond both boundaries, so they are represented by `UFH-006` as `ALLOW + W006`, independently of resource-safety limits.

## 3. Product scope frozen for this audit

- Input: project-defined KindleGen-compatible EPUB 3 subset.
- `.azw3`: KF8/AZW3 output.
- `.mobi`: one canonical Dual/combination MOBI layout consisting of a minimal KF7 compatibility section plus the canonical KF8 reading rendition. Full legacy MOBI7 reading-content parity is not a product goal.
- Unsupported source/target semantics must fail explicitly or be lowered only when the target behavior is externally justified.
- Exact KindleGen byte identity is **not** a requirement unless an individual field has an independent byte-level contract.
- Opaque/insufficiently documented auxiliary payloads (notably DATP exact contents) are not promoted to mandatory exact-parity requirements. If emitted, their record geometry must still be valid.
